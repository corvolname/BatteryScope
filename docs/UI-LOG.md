# 界面设计与迭代记录

整个应用只有两个界面：**菜单栏图标**和**点击展开的卡片**。卡片是纯实时视图——展开的那一刻立即读取一次，之后按刷新间隔（默认 1 秒）持续更新。

**菜单栏**：连续填充的电池图形（73% 就是 73%，不是最接近的五档之一）。

* **读数位置按供电状态决定**：

| 状态 | 电池图标内部 | 图标后方 |
|---|---|---|
| **接电源** | 只有居中的闪电 | 不显示 |
| 用电池 · 开百分比 | 百分比 | — |
| 用电池 · 开剩余时间 | — | `4h 15m` |
| 用电池 · 两个都开 | 百分比 | `4h 15m` |

  接电源时百分比和剩余时间都**不显示**：市电下没有"还能用多久"这回事，而百分比和闪电会争夺轮廓内那一小块空间。用电池时两个开关**互相独立**，各管各的位置。
* **电池整体保持窄**（28×15 pt，所有状态同一个尺寸），只比放得下 `100%` 所需的最小宽度略宽一点。收窄是全局的，不是只针对某个状态。
* **闪电是横向的，画在电池内部**。竖直闪电和这个字形是冲突的：电池轮廓宽约为高的两倍，竖闪电要么显得局促，要么得冲出边界才能有合理的尺寸。横放之后它均匀填满轮廓、不需要越界，而且照样读得出是闪电。路径先按竖直画好再旋转 90°，所以轮廓仍是真正的闪电形状，而不是手工凑出来的近似。
* 数字是从填充里「挖」出来的：与填充重叠的部分被擦除，落在空白处的部分正常绘制，所以在任何电量下都清晰可读。
* **图标区分供电状态**：接电源时电池内有一个闪电，用电池时没有。
* **图标与配色不可自定义**，只有三种状态：平时跟随菜单栏单色；**接着外接电源时整个电池变绿**；电量偏低/严重不足时转琥珀/红（优先于绿色）。

  绿色跟的是"**接电源**"而不是"正在充电"。macOS 经常停在 `AC attached; not charging`（维持电量），早先把颜色绑在 `isCharging` 上，结果是插上电**完全没有视觉变化**——看起来就像颜色没生效。现在绿色和闪电遵循同一条规则：都表示"在用外接电源"。
* **图标宽度恒定**，不随内容变化。这不只是为了整齐：状态栏项目宽度若变化，插拔电源时项目（以及它左侧所有项目）会整体位移，而**已展开的弹窗仍然锚在旧矩形上**——这正是"接电源时卡片不跟随图标"的原因。现在无论显示百分比、闪电还是什么都不显示，图标都是同一个尺寸。

### 插拔电源的反馈：修复被调用顺序吃掉了

第一次修这个 bug 时，我把电源状态改成 IOPS 优先——**但修复根本没生效**：

```swift
var snapshot = makeSnapshot(from: tree)   // ← 这里先从寄存器写入 isCharging / externalConnected
let powerSource = PowerSourceReader.read()
apply(powerSource, to: &snapshot)         // ← 我的 IOPS 覆盖在这里
```

`makeSnapshot` 在**同一个字段上先写了寄存器值**，所以 IOPS 的覆盖反而是被覆盖的一方。供电状态实际仍取自 30–60 秒粒度的寄存器。

更值得记的是：**我为此写的那条"实机一致性"断言通过了**——它只比对某一时刻快照与 IOPS 是否相同，而那一刻寄存器恰好是新的，于是给了我完全不该有的信心。现在换成验证**合并顺序**：构造"寄存器滞后、IOPS 已更新"的场景，断言 `apply` 之后必须是 IOPS 的值。这类 bug 只有顺序断言抓得住。

### 更早的判断：问题不在通知机制，在数据来源

IOPS 通知一直在正常工作，但**快照里的供电状态读的是电池节点寄存器**：

```swift
snapshot.isCharging = p.bool("IsCharging") ?? false        // 30–60 秒才发布一次
snapshot.externalConnected = p.bool("ExternalConnected")   // 从未使用 IOPS
if let charging = powerSource.isCharging, !snapshot.isCharging { ... }  // 只单向升级
```

`AppleSmartBattery` 每 30–60 秒才整体重新发布，所以**拔掉电源后寄存器仍说 `ExternalConnected = true`，闪电最长会多留一分钟**。IOPS 由 powerd 在电源变化的当下更新，而我们的 IOPS 通知也在那一刻触发——所以现在 IOPS 优先，寄存器只作为兜底。

这一条有直接断言覆盖（不需要真的拔插）：构造一个"寄存器说接着电源、IOPS 说在用电池"的快照，断言结果必须是**没接电源**；反向同理。另有一条实机断言核对快照与 IOPS 当前状态一致。
* **偏好设置里只有功能开关，没有任何说明文字**。

### 应用之前用的是旧外观：根因是二进制里记录的 SDK 版本

详情窗口的控件一直是 macOS 26 之前的样子（分段控件选中项是白色药丸 + 分隔线），而系统设置里是**蓝色实心胶囊**。原因**不是**用错控件，也不缺 API：

`LC_BUILD_VERSION` 里记录着应用"链接时所用的 SDK"，macOS 正是据此选择**兼容外观**。SwiftPM 因为 `platforms: [.macOS(.v14)]` 把部署目标和 SDK 版本**都写成了 14.0**：

```
LC_BUILD_VERSION
    minos 14.0
      sdk 14.0      ← 系统据此判定：这个应用是旧 SDK 时代的，给它旧外观
```

即使 `SDKROOT` 指向 26.5 也没用——记录的字段才是判据。Apple 在 Xcode 里这两个值是分开的，所以解法是显式告诉链接器：

```swift
linkerSettings: [.unsafeFlags([
    "-Xlinker", "-platform_version", "-Xlinker", "macos",
    "-Xlinker", "14.0",   // 最低系统仍是 14，老系统照常能跑
    "-Xlinker", "26.5",   // 但声明链接的是 26.5 SDK
])]
```

改成 `minos 14.0 / sdk 26.5` 之后，外观立刻切换：分段控件变成蓝色胶囊、**标签页移入标题栏**、窗口变成统一表面。

这一改也带出三个连带问题，都已修：

| 连带问题 | 原因 |
|---|---|
| 页签移入标题栏后，表头被压在标题栏底下（充电圆环顶部被切） | 窗口是 `.fullSizeContentView` + `titlebarAppearsTransparent`，内容延伸到标题栏下。改为标准标题栏即可，而 macOS 26/27 的标准标题栏本身就是玻璃工具栏 |
| 范围选择器写死 330 pt，胶囊控件更宽后溢出，压在采样点计数上（"30 天归档采样点"） | 去掉写死宽度，让控件按内容取自然宽度 |
| 满电接电源时容量条变成黑色实心 | `stateColor` 只在 `isCharging` 时返回绿色，而 macOS 在"插电且已充满"时报告 `isCharging = false`，于是落到 `.primary`。菜单栏图标早先已按"接电源即绿色"处理，改为同一规则后两处一致 |

另外**采样相位差异无法消除**：两个应用各按自己的定时器轮询同一批寄存器，相位不同就会在同一秒读到不同值。

#### 最终答案：SMC 的 `B0AC` × `B0AV`，既实时又自洽


| 方案 | 实时？ | 自洽？ |
|---|---|---|
| 整机取 SMC + 电池取节点 | ✓ | ✗ 变化时互相矛盾（用户看到的 9.37 / −20.32） |
| 三块全取节点 | ✗ 几十秒不动 | ✓ |
| **三块全取 SMC** | **✓** | **✓** |

关键在 SMC 有一组完整电池键，之前一直没查：

```
B0AC = -2008   [si16]   电池电流 mA（有符号，负=放电）
B0AV = 12465   [ui16]   电池电压 mV
B0AT = 3062             电池温度 30.62 °C
B0DC = 8694  B0FC = 7810  B0CT = 115
```

**`B0AC × B0AV` 就是电池功率**，带符号、在 SMC 里、每秒更新。之前用的 `PPBR` 不是电池功率（充电时约为真值的四分之一且反向变化）。

每秒采样实测：

```
 PSTR    B0AC(mA)  B0AV(mV)  B0AC×B0AV   与 PSTR 的关系
21.91      -1725     12498     -21.56    ✓ 自洽
21.54      -1979     12486     -24.71    差 3W（两次读取之间的真实负载波动）
24.71      -1745     12486     -21.79    差 3W
```

`PSTR` 和 `B0AC` **每秒都在变**，所以卡片是活的；而 `PDTR ≈ PSTR + B0AC×B0AV` 在几瓦内成立，所以三个数不打架。


### 三个功率必须来自同一个来源（用户问「整机 9.37、电池 −20.32 怎么理解」）

用户看到卡片上 `整机功耗 9.37` 与 `电池功率 −20.32` 并存。**用电池时这两个数必须互为相反数**（没有适配器，电池供的就是整机所耗），所以这组数字**不可能同时为真**。

原因是**混用了两个来源**：`整机功耗` 取自 SMC 的 `PSTR`，`电池功率` 取自电池节点。同刻实测：

| SMC `PSTR` | 节点整机 | 节点电池 |
|---|---|---|
| 22.38 | **9.87** | −9.87 |
| 22.99 | **20.88** | −20.88 |
| 20.65 | **20.88** | −20.88 |

**节点每一次都自洽**（电池 = −整机），而 `PSTR` 最多差 12 W。两者刷新节奏不同，负载一变就出现那种"互相矛盾"的读数。

这同时解开了上一轮的一个误判：我曾说对照应用的系统功耗比我们低约 2 W 是"它做了平滑"——**错了**。它显示 25 W 时节点的值是 25.75 W，**完全吻合**；它用的就是节点，用的是 `PSTR` 的是我们。

**改法**：三块功率（整机 / 电池 / 适配器）**全部取自电池节点**，同一来源、同一时刻，因此永远自洽。代价是刷新节奏跟随节点（不再有 SMC 的每秒更新），换来的是三个数不会互相打架——这正是用户提出这个问题的原因。

`smcPower` 仍保留，但只用于电池温度（`TB0T`）与风扇（`F0Ac`）。

### 电池功率曾经取错寄存器：SMC 的 `PPBR` 不是电池功率


查下来**我们这边有一个真 bug**：卡片上的「电池功率」取自 SMC 的 `PPBR`，而在这个硬件上**它不是电池功率**。

用**守恒律**判断——适配器输入 = 整机负载 + 电池功率——同刻读数：

| 时刻 | SMC `PPBR` | 电池节点 `BatteryPower` | `V×A` | 守恒校验 |
|---|---|---|---|---|
| 21:13:21 | 1.71 | **7.16** | 6.87 | 25.75 + 7.16 = **32.91 = Pin** ✓ |
| 21:13:47 | 1.77 | **6.32** | 6.32 | 26.37 + 6.32 = **32.69 = Pin** ✓ |
| 21:14:13 | 1.70 | **6.32** | 6.32 | 26.37 + 6.32 = **32.69 = Pin** ✓ |

`PPBR` 在充电时约为真值的四分之一，而且**与真值反向变化**（1.71 对应 7.16，1.77 对应 6.32）——它是另一个物理量，不是被缩放的同一個量。`PSTR` / `PDTR`（整机 / 适配器）与节点值一起能满足守恒律，所以那两个继续用 SMC。

**改法**：电池功率改为取电池节点的值。代价是刷新频率：节点遥测的更新稀疏（卡片上那条曲线会出现台阶），换来的是数值正确。

**这个 bug 是怎么活下来的**：当初引入 `PPBR` 时只在**放电**状态下核对过（那时它恰好接近真值 ✓），从未在**充电**状态下核对——而错误只出现在充电时。

**代价与取舍**：正确的来源刷新较慢，所以卡片上电池功率的曲线会出现台阶，不再像整机/适配器那样每秒平滑变化。「供电 · 实测（秒级）」这个分组标题对这行因此不那么准确。

### 另一个无法消除的差异：采样相位

即使两边读同一批寄存器，两个应用各自按自己的定时器轮询，**采样时刻不同**。电池寄存器的功率键约每秒更新一次，两个应用相位不同就会在同一秒里读到不同值——所以两边的曲线在时间上不可能逐点重合，只能保证**取值范围一致**。这是并行采样固有的，不是 bug。

### 面向用户的提示里不留固件原始代码

「提示」区曾经显示过一句：

> 充电器硬件限流回退已触发（reason = 16）。

读的是 `ChargerData.ChargerHwIlimBackoffReason`。**它对普通用户没有意义**，原因有三：

1. **16 是未公开位掩码里的一个 bit**（0b10000）。Apple 没有文档说明每一位的含义，把它原样打印出来等于要求读者去解释一个无法解释的数字。
2. **它在完全正常的状态下触发**：当时 `FullyCharged = 1`、`IsCharging = 0`、`ChargingCurrent = 0`、适配器已协商到 139.7 W——电池充满、充电正常停止，充电器 IC 自然把输入电流收回去，因为没有东西可充。这不是故障。
3. **措辞有误导性**：「限流回退」听起来像出了问题，用户却对它无能为力——既 alarming 又不 informative。

所以这条提示**整个移除**。同类问题一并清理：`SlowChargingReason = N`、`ChargerInhibitReason = N` 也不再回显代码，改为说清现象（"充电器报告充电速度较慢"、"充电已暂停，可能是温度或电源策略所致"）；累计温度限流时长从"秒"改为分钟/小时，且不足一分钟不显示。

留下的都是有现象、且用户能采取行动或理解的：电池温度偏高、充电缓慢、充电暂停、健康度低于 80%、协商功率低于标称。

自检里加了 5 项断言：合成数据里故意放入 `ChargerHwIlimBackoffReason = 16`、`SlowChargingReason = 7`、`ChargerInhibitReason = 3`，断言不再产生限流回退提示、正文不含任何原始寄存器取值、但"充电速度较慢"仍要被报告。

### 详情窗口的卡片：4 张，不是 8 张

窗口和文本报告用**两套**分组，`detailSections()` 与 `reportSections()` 分开：

| 处理 | 对象 | 原因 |
|---|---|---|
| **移除** | 容量 | 头部圆环已图形化电量，总览卡片的健康度环 + 「真实容量 / 设计容量」+ 进度条已图形化容量与健康度，这张卡片基本在复述 |
| **合并** | 电气 + 系统功耗 + 电芯组 → 电气与功耗 | 三张各只有 3 行，网格把同一行的卡片拉到最高者，于是三张全被撑出空白 |
| 不参与网格 | 概览、提示 | 窗口自己单独渲染 |

**代价要说清楚**：容量卡片独有的两行——`标称满充容量` 和 `相对设计容量的衰减`（mAh）——从此只出现在文本报告里（右键 →「复制电池报告」）和 CLI，窗口里看不到。如果哪天想找回来，位置是总览卡片左区。

#### 更正：我上一轮说"修好了"，其实菜单一直是折叠状态

上一轮我把菜单窗口的 `y=40` 当成修好的证据，并把 `h=122` 一并记下却没多想。**128 才是完整高度**（`contextMenu.size.height`），122 是被折叠的状态——少了 6 pt，正是滚动箭头占的地方。

| 内缩 | 菜单 y | 高度 | 状态 |
|---|---|---|---|
| 0 | 40 | **122** | 折叠 ✗ |
| 4 | 40 | 126 | 折叠 ✗ |
| **8** | **42** | **128** | 完整 ✓ |
| 12 | 46 | 128 | 完整 ✓ |
| 16 | 50 | 128 | 完整 ✓ |

取 8（最小的可用内缩），菜单落在 y=42，与系统苹果菜单的 y=40 相差 2 pt。连续三次启动复测均为 `y=42 h=128`。

### 右键菜单低了 27 pt：位置是量出来的，不是看出来的

菜单显示正常，只是**位置偏下**——这种问题从截图上判断不了（截图有缩放，肉眼估计不出 27 pt）。所以做了两步测量：

1. **定位状态项**：应用内报告按钮窗口 `{{1820, 1277}, {33, 65}}`；
2. **对照系统菜单**：点开苹果菜单，量到它在新窗口 `y=40`，而菜单栏底在 `y=39`（1 pt 间距）。

我们自己的菜单在 **`y=66`** ✗ —— 低了 26 pt。

**根因**：原来用 `statusItem.menu = …` + `performClick(nil)`，这条路径把菜单锚定在状态项的**窗口**下方，而该窗口在此 macOS 上是 **65 pt 高、且向上超出屏幕 13 pt**，于是菜单被推到 66。

改为显式定位：

```swift
let menuBarHeight = screen.frame.maxY - screen.visibleFrame.maxY
contextMenu.popUp(positioning: nil,
                  at: NSPoint(x: window.frame.minX, y: screen.frame.maxY - menuBarHeight),
                  in: nil)
```

修复后同一测量给到 **`y=40`**，与系统菜单一致；截图里也出现了 macOS 现代的菜单缺口，指向状态项。

**这一轮的教训**：能"看出来"的缺陷未必能量出来，而能量出来才能确认修好。中途我试过把图标换成品红块做像素定位，没能生效就放弃了——**对照系统自身的行为**（苹果菜单）是更省事也更可靠的办法。

### 闪烁的真正原因：`didResignActive`，不是（只是）点击监视器

第一次修的是全局点击监视器——**那是错的（或者说只是次要原因）**。加了事件追踪并用合成真实点击复现后，序列是这样的：

```
handleClick → togglePopover(isShown=false) → showPopover    第一次点击：展开
didResignActive → closePopover                              第二次 mouse-down：应用失去激活
handleClick → togglePopover(isShown=false) → showPopover    20 ms 后 mouse-up：重新展开 ← 闪烁
```

**点自己的状态栏图标也会让应用失去激活**（那一下由系统处理）。`didResignActive` 观察者于是把卡片关掉，而按钮动作在 **mouse-up** 才触发，那时读到的 `isShown` 已经是 false，于是"要关闭"被当成"要展开"。

修法：失去激活时如果**指针正落在自己的图标上**，就不在那里关闭，把决定权留给切换逻辑；其它原因的失活（切到别的应用）照常关闭。

两处都需要：全局监视器也要跳过图标上的点击，否则它会在 mouse-down 时抢先关闭，结果一样。

### 我在这轮犯的流程错误（比 bug 本身更值得记）

用户反馈"依然存在"时，我的修复其实**从未生效**，而我自己没发现：

**自检失败会挡住打包**（这是有意的设计），而当时有一条断言在失败——于是我这几轮 `make app` 都没有产出新包，**我一直在测旧二进制**并据此判断"修好了"。

那条失败断言还是我自己早先写坏的：

```swift
expect(registry.externalConnected, "顺序：寄存器当前报告已接外接电源")   // 读实机 IORegistry
```

它把**一次观察当成了不变量**。用户拔掉电源后它就失败，于是挡住打包、掩盖了真正的修复。已改为用合成快照验证**顺序**本身（拔电与插电两个方向都验证），不再依赖机器状态。

教训：`❌ 自检失败` 出现在 `make app` 的输出里时必须当成硬错误处理——它同时也意味着"你现在测的不是你以为的那个二进制"。

### 用电池时"输入侧"读数显示 — 而不是 0

在电池状态下截图验证固定 schema 时发现：`适配器转换损耗` 显示 `0.00 W`、`输入电压 / 电流` 显示 `0.00 V / 0 mA`。寄存器对"没有的东西"回答 0，而 0.00 V 读起来像是测到了什么。现在这两行在未接电源时显示 `—`。

### 点第二次反而重新展开（闪烁）：全局点击监视器也看到了这次点击

症状：点图标卡片展开，再点应该收起，但卡片**重新展开**并闪一下。

根因是事件顺序。关闭卡片靠两个手动监视器（没用 `.transient`，见下面的注释）：

```swift
globalClickMonitor = ... { self.closePopover() }   // 旧代码：没有排除"点在自己图标上"
```

原注释写着「全局监视器收不到本应用的事件，所以点图标纯粹是切换」——**这句不完全对**：应用处于未激活状态时，落在状态栏图标上的 mouse-down **仍会到达全局监视器**。于是：

1. 监视器先把卡片关掉；
2. 随后 `handleClick` 执行，发现卡片已关闭 → **重新打开**。

修法是让监视器先判断点击是否落在图标按钮内：

```swift
if self.clickIsOnStatusItem { return }   // 交给切换逻辑处理
self.closePopover()
```

判断用的是**按钮自身的 bounds**，而不是状态栏窗口的矩形——后者是私有实现，宽度语义不可依赖；点在隔壁那个状态栏图标上仍应算「外部点击」并关闭卡片。

验证用 `BATTERYSCOPE_TEST_CLICKGUARD=1`，它给出四组坐标的判断并确认实时指针路径：

```
图标中心 -> true      按钮边角 -> true
按钮外侧 -> false     真实指针移到图标上 -> true
```

### 验证这段代码时踩的两个坐标坑（与产品无关，但值得记）

第一次跑验证时有两项「失败」，**都是我的测试错了，不是代码错了**：

| 现象 | 真实原因 |
|---|---|
| 把指针移到图标上，实时判断却是 false | `CGWarpMouseCursorPosition` 用**左上原点**，AppKit 用**左下原点**。直接传 AppKit 坐标会把指针镜像送到屏幕另一端（实测落到 `{1836, 20}`，正是镜像位置） |
| 按钮边角判断为 false | `CGRect.contains` 是**半开区间**，正好落在 `maxX`/`maxY` 边上被判为外部。测试点需向内缩 1 pt |

顺带纠正一个我记错的数据：屏幕是 **2056×1329**，不是 1290（1290 是截图区域的高度）。

### ⌘W 关不掉详情窗口：应用根本没有主菜单

窗口是 `.closable` 的、关闭按钮也能用，但 **⌘W 毫无反应**。原因不在窗口：**快捷键是靠 `NSApp.mainMenu` 分发的**，而这是个 `LSUIElement` 附属应用，从来没有主菜单，所以那条捷径没人接收。

受影响的不止 ⌘W——**⌘Q、⌘M、⌘C、⌘A 同样失效**，因为同一个原因。

补上一个**永远不可见**的主菜单（附属应用不显示菜单栏，它只为让快捷键有处可去）：应用菜单（关于/隐藏 ⌘H/退出 ⌘Q）、文件（关闭窗口 ⌘W）、编辑（拷贝 ⌘C / 全选 ⌘A）、窗口（最小化 ⌘M）。菜单项**不设 target**，让动作沿响应者链走到当前 key window——所以同一个「关闭窗口」对详情窗口和偏好设置窗口都生效。

### 这条路径怎么验证

脚本无法把 accessory 应用置前（`open -a` 也不行，macOS 不允许抢焦点），所以**按键注入测不到这条路径**——用 `osascript` 发 ⌘W 只会把它送给当前最前面的别的应用。

改为在应用内部合成同一个事件，走完全相同的分发路径：

```
BatteryScope: 主菜单 -> ... 关闭窗口[w:performClose:] ...
BatteryScope: ⌘W 前 visible=true key=true
BatteryScope: performKeyEquivalent 返回 true
BatteryScope: ⌘W 后 visible=false        ← 窗口真的关了
```

钩子是 `BATTERYSCOPE_TEST_CMDW=1`。它验证了菜单项存在、快捷键匹配、动作经响应者链找到窗口、窗口确实关闭——唯一没覆盖的是「系统把按键递交给菜单」这一步，那是系统行为。

顺带确认 AppKit 自动补上了「全部关闭 ⌘⌥W」以及编辑菜单的写作工具/听写/表情与符号。

### 窗口卡片是固定 schema，不随电源状态变化

之前窗口的卡片是从文本报告里筛出来的，于是**插拔电源会改变卡片内容**：拔掉充电器，充电器那几行直接消失，同一行另一张卡片就短了一截，两列的行全错开。这是「接电和拔电后显示不固定」的根因——不是排版问题，是结构问题。

现在每张卡片的行**逐条列在 `detailSections()` 里**，值按标签去文本报告里取，**取不到就填 `—`，而不是让行消失**：

| 卡片 | 固定行数 |
|---|---|
| 电气与功耗 | 8 |
| 充电器与供电 | 8 |
| 寿命统计（电芯记录） | 7 |
| 标识 | 7 |

电芯组也固定三行（本机三个 bank）。bank 更少的机器会显示 `—`：行数是**布局的一部分**，不能由机器决定。

### 顺带清掉的重复读数

文本报告容忍重复，仪表盘不能：

| 重复 | 处理 |
|---|---|
| 标称功率 / 协商功率上限 / 输入功率上限（PMU 协商）——适配器处于最高档时三者是同一个数字 | 只留**标称功率**；协商电压与电流仍在，协商功率从中可见 |
| 整机负载 / 实际输入功率（`SystemLoad` / `SystemPowerIn`）——电池不贡献电流时是同一个读数 | 只留**整机负载**（拔电后它仍有意义） |
| 电池序列号（总览 + 标识） | 只在**标识** |
| 电量计芯片（总览 + 标识） | 只在**总览** |
| 电池功率 0.00 W 与其分量 | 保留（寄存器值与其分量，不是同一个数） |

### 自检如何保证这件事

窗口不再依赖实机状态即可断言：

- 卡片标题与顺序**固定四张**；
- 行数**固定 `[8, 8, 7, 7]`**，且每一行两张卡片行数相等；
- **空快照的卡片结构与行数完全不变**，且每个值都是 `—`——这比"拔掉电源"更强的条件，它保证了结构不依赖数据。

### 对齐的机械保证：每行只有一行高

「行数相等」还不够。第一版做到 9/9 之后**行依然对不齐**，因为 `USB-PD 档位（HVC 菜单）` 把四个档位逐条列出，值是两行——从它开始，右侧下面每一行都错开一行。

两个修法并用：

1. **窗口给单行摘要**：`15 / 27 / 45 / 100 W`；逐档明细（`15V×2.99A=45W` 等）留在文本报告里，那里不需要对齐。
2. **`KeyValueRow` 增加 `singleLine`**：详情窗口的 11 处调用全部启用，标签和值都限定一行，**宁截断不换行**。截断的尾巴看得出来是被截断，而错位的列会被当成排版错误——前者是较小的恶。

自检加了一条机械断言：**窗口里任何行的标签或值都不得含换行**，并要求 USB-PD 那一行确实是单行摘要、标签不含内部术语 `HVC`。合成数据里特意放了**两个** PD 档位，否则这条断言没有牙齿（单档位天然就是一行）。

### 对称规则：标题齐平、行数相等、标签不重复

详情窗口的四张卡片按两条机械规则排布：

1. **同一行两张卡片的标题在同一水平线上；**
2. **两张卡片的项目数相等**（行数相等 → 高度相等 → 标题与逐行都对齐）。

为此把重复的标签各自只留一处：

| 标签 | 只保留在 | 理由 |
|---|---|---|
| 电池序列号 | 标识 | 身份信息属于标识卡片 |
| 电量计芯片 | 总览 | 它是所有容量读数的来源，属于总览 |

`电量计芯片` 因此从 `detailSections()` 里剔除（总览卡片是视图自己构建的，不走那个函数）。配平结果：**9/9** 与 **7/7**。

总览卡片内部同样按 5/5 排：

- 左列（状况与散热）：电池状况、电池温度、CPU 温度、GPU 温度、风扇转速
- 右列（容量与时间）：电量计芯片、当前剩余容量、相对设计容量的衰减、标称满充容量（模型值）、预计充满/续航时间

**预计时间这一行即使取不到值也占位**（显示 `—`）：按状态增减行会让两列错位，而不错位正是这一行存在的意义。满电接电源时它就是 `—`（系统不给充满估计）。

自检新增一条机械断言：**窗口里同一个标签不得出现两次**——这正是「电池序列号在总览和标识里各有一个」那一类问题的通用检查。

### 窗口里的行不带注解，也不带两行诊断

窗口的行此前带着注解，分三类，**对窗口的读者都没有用**：

| 类型 | 例子 |
|---|---|
| 寄存器路径 | `PowerTelemetryData.SystemPowerIn`、`PowerDistribution.IPDInputPower`、`PowerTelemetryData.SystemLoad` |
| 单位重复（值本身已给出） | `28000 mV · 4990 mA`（值就是 `28.00 V / 4.990 A`） |
| 原始编码的说明 | 「固件未提供标准日期，此处为原始编码」、「ATL」 |

它们还有一个副作用：带注解的行是两行高，**两列的行走线因此错开**。注解去掉后每行都是单行，左右两列逐行对齐。

同时移除两行诊断：**PMU 允许充电**、**未充电原因**——接电源且满电时 macOS 报"不允许充电"并给出一个十六进制原因码，既不 actionable 也读不懂。

**这些全都在文本报告里保留**（右键 →「复制电池报告」）。窗口做取舍是因为它有图形、有固定网格；文本报告是线性的，注解在那里正合适。自检断言的是这个分工：窗口注解数为 0，且文本报告的注解**没有**被连带剥离。

### 总览右侧填满，并补回丢失的两行

删掉「容量」卡片后，它独有的两行一度无处可去；总览卡片右侧又正好有留白。于是：

- 右列一（状况与散热）：电池状况、电池温度、CPU 温度、GPU 温度、**风扇转速**（从原硬件列移来，同属散热）
- 右列二（硬件与容量）：电量计芯片、电池序列号、**当前剩余容量**、**相对设计容量的衰减**

左区（两个环 + 容量说明 + 进度条）约 120 pt，每列 4–5 行正好齐平，留白消失。

`标称满充容量` **故意不放回来**：它必须配「电量计模型值，非实测」这句说明才能被正确理解，而窗口已不再显示行的注解。

### 卡片不再等高拉伸

之前同一行的卡片会被拉到最高者的高度（`fillsRowHeight`）。合并掉三张短卡片后，留白只是**转移**了——容量卡片比新的邻居矮四行，空白照旧。

所以拉伸本身去掉了：卡片贴合内容，行内自然长短不一。合并 + 贴合之后，实测四张卡片两两高度接近（9 行 vs 11 行、7 行 vs 8 行），既没有卡片内部留白，也没有明显的参差。

### 健康度配色：只有 80% 以下才是黄色

原来是三档：<80% 红、<90% 黄、≥90% 绿。**中间那一档是自造的**——macOS 没有 80–90% 这个警告区间，结果一块完全健康的 89% 电池被涂成黄色。

macOS 自己用的分界就是 **80%**：低于它，系统设置会把电池标为需要维修（`BatterySnapshot.condition` 也是 `health < 80 -> serviceRecommended`）。现在配色与它一致：

| 健康度 | 颜色 |
|---|---|
| < 80% | 黄色（需要维修） |
| ≥ 80% | 绿色（正常） |

自检里加了两条边界断言把这个数字钉住：健康度正好 80.0% → 正常，79.0% → 建议维修。因为阈值取的是 `< 80` 而不是 `<= 80`，正好 80 属于正常。

### 说明文字改为「真实容量 / 设计容量」

健康度环下方原本只写设计容量。现在写全产生这个百分比的两个测量值：

> 真实容量 7,779 mAh / 设计容量 8,694 mAh

左区因此从 188 pt 加宽到 250 pt 以容纳一行，同时**把圆环组在列内居中**——此前环是左对齐、文字是居中的，两者轴线差了半个宽度（实测 10 pt）。

### 实时图表页：把墨迹减掉

用户反馈"图表有点多看不懂"。**我第一次判断错了方向**：以为是指标名太术语化，于是把「CPU 温度」写成「处理器温度」、「整机功耗」写成「电脑耗电」。用户随即纠正——*"不是指标名换成普通话的问题，常用的比如 CPU GPU RAM DSK PWR 这些缩写还是能看懂的，就是图表太乱了"*。

命名已**全部还原**（只保留一处：`温度` → `电池温度`，因为它和「CPU 温度」「GPU 温度」并列时说不清是哪个）。

真正的问题是每张图上的墨迹。一张图原本有：

| 元素 | 数量 |
|---|---|
| 虚线纵向网格 | 5 条（每条还带刻度和时间标签） |
| 虚线横向网格 | 4 条 |
| 右侧刻度标签 | 4 个 |
| 「区间 a → b」 | 1 处，且复述两端刻度 |
| 面积渐变填充 + 折线 | 2 层 |

两张图就是四十来处墨迹。而时间跨度**已经由上面的范围选择器说明了**（"最近 5 分钟"），网格和刻度大多没在传达折线形状之外的信息。

改后：

- **网格全部去掉**（纵向、横向都不画）；
- 时间标签 5 个 → 3 个；
- 右侧刻度 4 个 → 3 个，且**平直时不画**；
- 「区间 100.0% → 100.0%」→ 白话总结「一直是 100.0%」/「最低 14.83 W · 最高 33.03 W」；
- 移除「9 个采样点」与底部「区间统计」卡片（要点已并入每张图）；
- 默认 2 张图（原 3 张）；
- 顺带修掉一个渲染 bug：面积填充会画到 frame 之外（`.frame(height: 150)` 的红框实测 148 pt，填充却延伸 300 pt 以上），加 `.clipped()`。

**这里的教训**：用户说"看不懂"时，我直接跳到了"改文案"，而实际问题是**信息密度**。应该先问是哪一类问题——术语、密度、还是布局——而不是假设。

### 应用图标重画（启动台 / Dock 那个）

旧图标是**绿色圆角方块 + 白电池 + 闪电**——平台上几十个电池工具都是这个样子，而且闪电让它在任何电量下都读作"正在充电"。

新图标用应用自己的识别符号：**界面里到处都是的圆环仪表**。

- 深色板岩底（顶部微亮、底部更深）+ 环后一层绿色柔光，避免小尺寸下变成一块死黑；
- **圆环仪表**：270° 弧、缺口在正下方，青绿→绿渐变，圆头端点——不是"圆圈"，是"表盘"；
- 环内一颗**白电池**，约 68% 电量。

**一处必须实测才发现的问题**：第一版电池宽度取 `0.335 × 边长`，256px 下好看，**32px 下电池两侧贴住圆环、两形状糊成一团**。改成 `0.238`（不到环内空间的一半）后小尺寸才立得住。图标不是"在最大尺寸下好看"就行的。

### 一个把 CPU 吃到 17% 的陷阱：关掉却还活着的视图

应用常驻时曾被测到 **17% CPU**（对照应用约 2.5%）。用累计 CPU 时间法（比 `top` 采样可靠得多）分状态测量后，问题定位得很清楚：

| 状态 | 修复前 | 修复后 |
|---|---|---|
| 卡片从未打开 | 1.0% | **0.6%** |
| 卡片打开后**真的关闭** | 2.5–4.5% | **0.6%** |
| 卡片保持打开 | 7.3% | 7.3% |

**根因**：`popover.contentViewController` 在第一次打开后**永久存活**。所以卡片一旦被点开过，它的 `body` 就会每秒重新求值、图表每秒重画——即使窗口早就关了。再叠加充电时那条 30 fps 的脉冲动画（同样在不可见的视图里继续跑），就凑出了 17%。

**修复**：实现 `NSPopoverDelegate.popoverDidClose`，关闭时把 `contentViewController` 置空。下次打开重建，成本可以忽略——卡片显示的数值都存在 monitor 里，不在视图里。顺带把脉冲动画从 30 fps 降到 12 fps（条纹是缓慢平移，多余帧纯属浪费）。

修复后"关闭"与"从未打开"基本相等（1.4% vs 1.3%），说明视图确实被释放了。


后来把每秒的 HID 温度扫描换成 SMC 读取（见上），idle 又降到 **0.6%**。

**剩下没解决的**：卡片打开时约 8.6%，来自每秒一次、每次约 65 ms 的完整 SwiftUI 布局。我实测排除了三个猜测：

| 假设 | 实验 | 结论 |
|---|---|---|
| `sizingOptions` 每次更新都重算布局 | 改为固定尺寸 | 只降 1.2 个百分点，不是主因 |
| 每秒发布 7 次状态导致多渲染 | 去掉 4 个 `@Published` | 无变化——SwiftUI 确实在同一个 runloop 轮次内合并了 |
| 折线点数过多（600 点画在 290 px 上） | 降到 160 点 | 无变化 |

用计数器直接验证过：卡片 `body` **精确地每秒求值 1 次**，没有冗余渲染。所以成本是单次布局本身，而非次数。

### 四个真实缺陷（都是这几轮发现的）

**三、彩色模式下数字是黑色的。**

`drawReading` 收了一个 `color` 参数却**从未使用**——`NSAttributedString` 自带 `.black` 前景色，于是低电量（红色）图标里的 `8%` 是黑的，和红色轮廓对不上。现在读数自带强调色：与填充重叠的部分被挖掉，落在空白处的部分就用这个颜色画。

**四、闪电的形态改了三轮，最后落在"横向、画在电池内部"。**

第一版竖直闪电是**空心**的：模板图像只保留 alpha，系统再用菜单栏自身的颜色填充它，所以被涂成不透明的闪电和同样不透明的填充融为一体，只剩下光晕形成的一圈空心轮廓。改成从衬底里"挖洞"后变成实心，但竖直闪电和宽扁的电池轮廓始终不协调——加宽会变成胖锯齿，收窄又显得局促，两端只得冲破边框才能有合理尺寸。横放之后两个问题一起消失：它均匀填满轮廓、不需要越界，而且是实心的白色闪电。

这段弯路也留下一条教训：**断言必须跟着设计走**。闪电从"挖洞"改成"叠加"之后，原来那条"接电源时的不透明像素更少"立刻失效（实测 254 == 254）——它测的是旧设计的实现细节。现在改成"渲染器唯一画出的近白色形状出现即算数"，直接测行为而不是测实现。


**一、闪电在单色模式下是隐形的——所以"接电源"和"用电池"看起来一样。**

正常电量下走单色，而单色图标是**模板图像**：系统只使用它的 **alpha 通道**，然后用菜单栏自身的颜色填充。原来闪电被涂成不透明白色画在同样不透明的填充上，两者 alpha 都是 1，于是**完全融为一体**：

```swift
NSColor.white.setFill()
bolt.fill()          // alpha = 1 → 和不透明的填充没有区别
```

现在闪电是**从填充里挖掉的洞**（先以 `.clear` 混合模式描一圈光晕，再填充闪电本体）。判据是"不透明像素数"：

| 状态 | 不透明像素 |
|---|---|
| 电池（无百分比） | 223 |
| **接电源（无百分比）** | **199** ← 少了 24 个 |
| 电池（有百分比） | 290 |
| **接电源（有百分比）** | **279** ← 少了 11 个 |

修复前这个数字只会相等或增加（"再涂一层不透明"），所以 `acPlain < batteryPlain` 正好是这次 bug 的回归断言。

顺带解决的重叠问题：百分比和闪电都居中时会叠成 `9⚡%`。现在两者同时显示时，闪电占左侧一条窄列、数字在剩余区域居中。

**二、剩余可用时间在"十几小时"和"几小时"之间反复跳。**

剩余时间本质是 `电量 ÷ 电流`，所以几秒的编译负载就能让 `10h 20m` 变成 `3h 05m`。它是个预测值，不该按实时读数的方式来显示。macOS 自己也用粗得多的节奏更新它。现在做了三件事：

* **5 分钟中位数**——中位数完全忽略尖峰，均值会追着尖峰跑。这是消除剧烈跳动的关键。
* **每分钟最多更新一次**——预测值变化很慢，每秒刷新只会显得不稳。
* **按 5 分钟取整**——底层值几乎没变时，数字不会抖动。

因此卡片标题和菜单栏时间**都不再逐秒变化**，而是每分钟至多移动 5 分钟。

### "数据明明是秒级的，为什么看起来还是不动"

我自己踩过这个坑，两个原因都不是数据源的问题：

**一、y 轴下限是按 60 秒跳变数据设的，把真实波动压平了。** 实测 40 秒的真实幅度：

|---|---|---|---|
| `PDTR` 适配器 | 28.94 – 33.69 W | 4.75 W | 20 W ← 只占 24% 高度 |
| `PSTR` 整机 | 23.90 – 27.22 W | 3.32 W | 20 W |
| `PPBR` 电池 | 1.61 – 1.73 W | 0.12 W | 20 W |
| PMU die 温度 | — | 约 1 °C | 6 °C |

20 W 的下限在 60 秒阶跃的时代是合理的（小于 20 W 的差都是量化噪声），但换成 1 Hz 连续信号后，它把真实波形压成一条近乎平的线。现在下限按实测幅度重设（适配器/整机 1.0 W、电池 0.15 W、PMU 0.5 °C），波形填满整个高度；纯浮点噪声（远小于 0.01 W）仍然显示为平线。

**二、显示精度把运动量丢掉了。** 格式化规则原本是"≥10 W 显示 1 位小数，<10 W 显示 2 位"：

```
电池功率 +1.73 W   ← <10 W，2 位小数，看起来一直在动
适配器   33.4 W    ← ≥10 W，1 位小数，看起来基本不动
```

两者数据源相同、刷新率相同，观感却相反，纯粹是小数位数造成的。SMC 返回 float32，本身有亚 0.1 W 分辨率，所以现在 **100 W 以下统一显示 2 位小数**（`34.99 W`），如实反映测量精度。

**三、还有一个我自己的 bug**：上一轮接入 SMC 时，我只把「整机功耗」的数值改成实时值，「适配器供电」和「电池功率」的数值仍读 60 秒寄存器——于是折线是活的、数值是死的。现在三个数值和三条折线都走 SMC。

**实时传感器（秒级）**：**CPU 温度**和**GPU 温度**，来自 SMC 的 `Tp`/`Te`（核心）与 `Tg`（图形）传感器。

### CPU 和 GPU 是怎么分开的（实测，不是猜命名）

PMU 的 HID 温度通道更快（亚秒级），但**无法拆成 CPU/GPU**。用 8 线程 CPU 负载和 Metal 计算负载分别实测后发现：**同一批通道在两种负载下都升温**（`tdev3`、`tdev6`、`tdie*`、`TP*g`）——热量在封装内扩散，差值分不开两者。

SMC 一侧则分得很干净。218 个温度键里按前缀测峰值升温：

| 前缀 | 键数 | 8 线程 CPU 负载 | Metal GPU 负载 |
|---|---|---|---|
| `Tp*` | 30 | — | +9.8 °C |
| `Te*` | 3 | **+7.7 °C** | +9.9 °C |
| `Tg*` | 8 | +4.0 °C | **+18.7 °C** |

`Tg*` 对 GPU 负载的敏感度是 CPU 负载的 **4.7 倍**，`Te*` 反过来对 CPU 最敏感。`Tp`/`Te` 是性能核与能效核传感器、`Tg` 是图形传感器——这与同类工具的惯例一致，也是本应用采用的分组：**CPU 温度取 `Tp*` ∪ `Te*` 中的最高值，GPU 温度取 `Tg*` 中的最高值**。

顺带省了 CPU：41 个键、每个两次 SMC 事务，约每秒 0.1% 单核；而被它替换掉的 HID 扫描是每秒 156 个服务、312 次事件拷贝。`PMUHIDReader` 保留下来供诊断使用（`batteryscope-cli pmu`），但不再在采样路径上。

### 两个真实缺陷（都是这次排查中发现的）

**一、`tcal` 是标定常数，不是传感器——而它一直是"最高值"。**

`tcal`（**cal**ibration）在每一次采样里都恒定 **51.85 °C**，而所有真实传感器都在 30–43 °C 之间每秒跳动：

```
tcal=51.85   ← 恒定，标定参考值
tdie4=39.70  ← 真实最高传感器
```

我原来直接取 26 个通道的最大值，于是"最高"永远解析到 `tcal`，卡片显示 51.9 °C——**比芯片真实温度高约 15 °C**，而且折线必然是一条平线（常数画不出波形）。现在 `tcal` 被显式排除，标题只在真实传感器中取最大值。

**二、`PPBR` 没有符号，放电会显示成正的。**

同一时刻对照：

| 状态 | SMC `PPBR` | 电池节点 `BatteryPower` |
|---|---|---|
| 充电 | +1.64 W | +12.4 W |
| 放电 | **+22.85 / +35.04 W** | **−22.15 W** |

`PPBR` 无论充放电都是正值——它是**功率量值**，不携带方向。所以放电时卡片显示过 `+24.45 W`，看起来像"电在往一块正在供电的电池里流"。现在量值取自 SMC、**方向取自电池节点**（只有它知道电荷往哪边走）：充电为正、放电为负。

顺带一提，`PSTR`/`PPBR` 在几秒内从 22 W 摆到 35 W 并不是噪声，而是**真实负载尖峰**（当时正在跑编译和截图）；电池节点显示的稳定 22.15 W 反而是 60 秒前的陈旧采样——这正是用秒级源的价值。

**电量进度条**：充电时填充部分显示**流动的斜条纹**（macOS 表达"进行中"的惯用视觉语言，读起来是"正在充入"而不是"电量在变"），放电时在条下方显示**预估可用时间**、充电时显示预估充满时间。

这个动画由 `TimelineView` 驱动显示链路，而不是 `repeatForever`：后者会被每秒一次的快照刷新打断，逐帧实测只出现 2 个不同帧；改用 `TimelineView` 后 **8/8 帧全不同**。

三条折线的当前值写在折线标题行右侧，因此**没有任何数字被打印两次**——这也是卡片顶部不再重复画一条"电量"折线的原因：电量已经是大标题了。三条折线都**不画零基线**（它们各自的最小量程已经把纵轴固定住），线条因此更舒展。

电池参数**按含义组合**，而不是一个值一行：

| 主标签 | 下方小字 | 右侧值 |
|---|---|---|
| 健康度 | 循环次数 114 / 1000 | 88.7% |
| 温度 | — | 35.2 °C |
| 当前容量 | 满充 7,708 · 设计 8,694 mAh | 6,754 mAh |
| 电压 / 电流 | — | 12.95 V · 2.90 A |

健康度与循环次数描述的是同一件事（老化），三个容量是同一个量在电池寿命三个时点的取值，所以它们各自合并为一条——7 个值只占 4 条的位置。

底部只有一个偏好设置齿轮。

> 曾经在底部放过一个"数据 X 秒前"的计时器，后来去掉了：它只是在**解释**数值为什么旧，并没有让数值变新，属于把系统限制转嫁给用户。真正的原因写在第七节。

三个功率量是三条独立的物理通路，配合起来能直接读懂正在发生什么。上面这张真实的充电瞬间截图里：`24.5 W（整机）+ 44.1 W（充电）= 68.6 W（适配器输入）`，而同一时刻的 `12.68 V × 3.48 A = 44.13 W` 也与电池功率一致——两条独立计算路径互相印证。

卡片上**没有**提示、详情、复制、暂停按钮，也没有数据来源标注——数值就是数值。底部只有一个偏好设置齿轮。

**偏好设置**是独立的小窗口，只包含设置项本身：菜单栏样式、刷新间隔、历史记录、通知、开机自启。没有"关于"、没有数据来源说明、没有本机信息。

**详情窗口**（概览 / 实时图表 / 原始键值）不在卡片上，只从右键菜单进入，需要时才用：

* **概览**——总览仪表 + 容量/电气/充电器/电芯组/寿命统计，与 CLI 报告同源
* **实时图表**——可选指标（电量/功率/温度/容量/电压/健康度）× 时间范围（5 分钟 / 15 分钟 / 1 小时 / 本次会话 / 30 天归档），每指标独立坐标轴，附区间最小/平均/最大统计
* **原始键值**——实时抓取的 300 余个 IOKit 键，可搜索、按节点分组、显示类型，可整段复制

历史以每分钟一个点的形式追加到 `~/Library/Application Support/BatteryScope/history.jsonl`（保留 30 天）。

通过环境变量触发，正常使用永远不会激活：

BATTERYSCOPE_SHOW_CARD=1 \
  dist/BatteryScope.app/Contents/MacOS/BatteryScope        # 启动后自动展开卡片

  dist/BatteryScope.app/Contents/MacOS/BatteryScope        # 打开偏好设置窗口

  dist/BatteryScope.app/Contents/MacOS/BatteryScope        # 2s 开 / 4s 合 / 6s 开，
                                                           # 用来验证再次点击能收起卡片

BATTERYSCOPE_KEEP_CARD_OPEN=1 \
  dist/BatteryScope.app/Contents/MacOS/BatteryScope        # 卡片保持打开且强制显示。
                                                           # 脚本截图必需：macOS 14 起后台应用
                                                           # 无法自行抢焦点，AppKit 会把 popover
                                                           # 排到屏幕外，截图只能拍到背景。

有了这些就不必为了截图验证 UI 去申请辅助功能权限来模拟点击状态栏图标。

```bash
defaults read com.local.batteryscope

```

## 十四、已知限制

* **桌面 Mac 没有电池**——应用不会伪造数据，卡片与详情页会说明"此 Mac 没有内置电池"，菜单栏显示电源插头图标。
* **`ManufactureDate` 无法给出真实生产日期**——见第五节第 2 条。真实可用的厂商/批次信息来自 `MfgData`。
* **电池节点里的数据不是逐秒更新的**——`AppleSmartBattery` 由驱动每隔约 30–60 秒整体重新发布一次，这是系统行为，无法绕过。详见第七节。**但功率不依赖它**：三条功率曲线走 SMC，约 1 Hz。只有电量百分比、健康度、循环次数、当前容量这些仍受 30–60 秒粒度限制。
* **`Amperage` 在放电时可能为 0**——见第六节。此时功率是推算值并已标注；容量趋势（用于估算可用时间）仍基于 `AppleRawCurrentCapacity` 的实测斜率，不受影响。
* **健康度不做口径切换**——只有实测口径。想对比标称值请用 `dist/batteryscope-cli raw --filter NominalChargeCapacity`。
* **后台应用无法自行弹出卡片**——macOS 14 起，当你在别的应用里操作时，应用不能自己抢焦点，AppKit 会把 popover 排到屏幕外。你手动点击菜单栏图标是正常的（点击本身会授予焦点），只有脚本化验证需要 `BATTERYSCOPE_KEEP_CARD_OPEN=1`。
* **无法控制充电上限**——Apple Silicon 上没有可用的第三方接口，因此本应用不提供该功能。详见第八节。
* **未充电原因的文案部分为推断**——`NotChargingReason` 的位语义没有公开文档。只对已观测到与系统状态吻合的值给出解释，其余显示原始十六进制，不猜。
* **30 天归档需要时间积累**——新装的应用归档为空，归档图表在有数据前会提示数据不足。
* **`batteryscope-cli` 的 `raw --filter` 用的是正则**，`--filter 'A|B'` 是正则的"或"。
* 应用为本地临时签名（ad-hoc），未做公证；从网络下载后首次打开可能需要在"隐私与安全性"里放行。本机构建无此问题。
